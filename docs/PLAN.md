# 開発計画

仕様(docs/spec.md) → Lean 4 でモデル化・証明 → Lean 実行可能判定器をオラクル化 → Go 実装 → 差分テスト。

## 決定事項 (2026-11-24)
1. 時刻は **分単位の絶対時刻**(自然数)。場所間の移動時間を検査する。
2. エンディング条件は **ゴール達成 + プレイヤー選択** を変数に含む。
3. **知識・手がかり** の検査を MVP に含める。
4. エンディングは全パターンで **ちょうど1つ** に決まらなければエラー(優先度による解決はしない)。

## フェーズ
- Phase 0: 環境構築(elan/Lean, Lake, Go module, Makefile, CI)
- Phase 1: 仕様書 docs/spec.md
- Phase 2: Lean モデル化(Spec: Prop 仕様 / Checker: 判定関数 / Proofs: 健全性・完全性・不変条件・決定性)
- Phase 3: オラクル(`lake exe oracle`)と手書き+生成テストケース → testdata/oracle/
- Phase 4: Go 実装(Lean 定義と 1:1 対応)、YAML フロントエンド、CLI
- Phase 5: 差分テスト(ゴールデン + Lean オラクルを呼ぶライブ差分ファズ)
- Phase 6: CI で乖離防止(証明ビルド・オラクル再生成 diff・go test)

## Phase 4 完了 (2026-11-24, 仕様 0.5.1)

Go 実装(`go/`)を Lean の定義と1対1で書いた。

- `internal/model`: 型と正規化 JSON の読み込み。入力エラーの判定も Lean と同じ(キーの重複、数値の表記、空の ID など)
- `internal/check`: 意味論と全規則・正規順序。G 群は、パターンを Lean と同じ順で1つずつ生成しながら集計する(結果は同じで、メモリはパターン数に比例しない)
- `internal/yamlio`: 作者向け YAML(docs/yaml.md)→ 正規化 JSON。時刻「時:分」、キャラクターごとのタイムライン、ハンドアウトの時系列表
- `cmd/mmcheck`: `check`(text / json、`--strict`)、`convert`、`version`。終了コード 0 / 1 / 2
- サンプル `examples/yaml-demo`(YAML の見本)

確認:
- Go のゴールデン差分テスト: testdata/oracle の 300 件と examples の 3 件がすべて Lean オラクルの出力と一致
- その場での差分(新しい乱数の種のランダムシナリオ、ゴール・選択・エンディングを空にしたもの、サンプルの変異)1,800 件で不一致 0 件
- 数値の表記など入力エラーの境界 21 件で、Go と Lean の判定が一致

作業中に見つけて直したもの:
- 仕様 0.5.1: Lean オラクルの数値の扱いが一貫していなかった(`1.26e3` は受け付け、`1260.0` は入力エラー)。値が整数なら表記を問わないことにし、Lean を直した。キーの重複と、指数部が 100,000 を超える数(Lean の JSON パーサの制限)は入力エラーと明記した
- Lean: 値が 0 で負の指数がとても大きい数で、正規化が指数の回数だけ再帰していた
- Go: 変数もエンディングもないシナリオで G001 を出していなかった(空の割り当てを「反例なし」と取り違えていた)。ライブ差分で見つけ、回帰テスト edge/no_variables_no_endings を足した

## Phase 5 完了 (2026-11-24)

差分テストを整えた(詳細は testdata/oracle/README.md)。

- ゴールデン差分(`TestGolden`): testdata/oracle と examples の期待出力と Go の出力を比べる(Phase 4)
- ライブ差分(`make live-diff`, tools/oracle/live.py): その場で作ったシナリオで Go と Lean オラクルを比べる。入力はランダム生成・G 群を空にしたもの・サンプルと手書きケースの変異(mutate.py)・壊した入力。Go の並べ替え不変(定理 3)も確かめる。不一致の入力は testdata/live-failures/ に保存
- Go だけで動くテスト: 並べ替え不変(`TestPermutationInvariance`)、ファズ(`FuzzCheck`: パニックしない、出力が正規順序で重複なし)

結果:
- ライブ差分 4,500 件(種 1 と 2)で不一致 0 件。仕様の全 54 規則が少なくとも1回出た。入力エラー 411 件も判定が一致
- ファズ 60 秒(約 1,000 万回)で問題なし

## Phase 6 完了 (2026-11-24)

CI(.github/workflows/ci.yml)で、仕様・Lean・Go のずれを止める。

- Lean ジョブ: 証明のビルド、証明の監査(`tools/check_axioms.py`: sorry / admit / 独自の axiom がなく、主要な定理 20 個が標準の公理だけに依存する。`exists_valid` の native_decide だけ例外)、仕様バージョンの一致(`tools/check_versions.py`: 仕様書・Lean・Go・ケースの生成・サンプル)、テストケースと期待出力が最新か(`make diff-check`)
- Go ジョブ: gofmt、go vet、テスト(ゴールデン差分・並べ替え不変・ファズの種・YAML・CLI)
- ライブ差分ジョブ: Lean と Go の両方をビルドし、その場で作った 1,000 件で比べる(種は run_id)。毎日の定期実行では 10,000 件とファズ 5 分。不一致の入力は成果物として保存
- `make audit`、`make ci`(CI と同じ検査をまとめて実行)

確認: 新しく clone したリポジトリで `make ci` が通ることを確かめた(GitHub Actions 上での実行はまだ。初回の push で確かめる)。

## 仕様 0.6.0: ゴールの必要な知識と達成条件 (2026-11-24)

ゴールに `requires_knowledge`(入手可能でなければ達成できない)と `condition`(ゴール ⇔ 式)を加えた。これまで「秘密を探る」のような知識のゴールは書けず、達成条件は `constraints` に手で書いていた。

- 仕様: §1.8、§4.7 の導出制約 3, 4、R002 / R009 / R012 の対象に condition を追加
- Lean: `Goal` に2フィールド(`Formula` の決定可能な等号を手で書いた)。導出制約を `itemConstraints` / `knowledgeConstraints` / `conditionConstraints` に分け、定理 7 を `knowledge_iff`、`condition_iff` で拡張。並べ替え不変(clues / characters / goals)の証明を更新
- Go: 同じ導出制約。explain にゴールの節(達成される選び方の数は G004 / G006 と一致することをテスト)
- テスト: 手書きケース 11 件、ランダム生成に2フィールド
- サンプル: 六角館の6件と荒木コノミの3件の「ゴール ⇔ 投票」を constraints から condition に移した(検出結果は同じ)
