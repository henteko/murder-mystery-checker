早見表

規則コードの読み方

判定器の指摘は T003 のような「英字1文字 + 番号3桁」で表します。英字は何を調べる規則かを表すグループ、番号はグループ内の通し番号です。

R

構造(Reference)

ID の重複、存在しないものの参照、書き方の誤りなど、シナリオファイルそのものが壊れていないか。

T

タイムライン(Time)

移動時間、同時に2か所にいないか、その場所にいるか、死亡後に行動していないか。

I

所持品(Item)

持っていない物を渡していないか、使い切った物を使っていないか。

K

知識・手がかり(Knowledge)

知らないことを話していないか、真相にたどり着けるか、証言の時刻が合っているか。

H

ハンドアウト・盤面(Handout)

配るハンドアウトや盤面の記述が、タイムラインの結果と合っているか。

A

真相の断言(Assertion)

「18:00 に屋上には誰もいない」のような真相の主張が、タイムラインと合っているか。

G

ゴール・エンディング(Goal)

どの選び方でもエンディングが1つに決まるか、達成できないゴールはないか。

重大度は2種類です。error はシナリオの矛盾で、直す必要があります。warning は記載漏れなど、確認を勧めるものです。下の表で warning の規則には「警告」と付けています。

第1部

証明された11の約束

どの定理も、Lean の標準の公理だけに依存しています(定理6のみ、具体例の計算に Lean のコンパイラを使います)。

定理1

判定器は見逃さないし、誤検出もしない

意味: 「移動時間が足りない」と言われたら本当に足りていないし、足りていなければ必ず言われます。

定理2

どんな選び方でもエンディングはちょうど1つ

定理3

書く順番を変えても結果は同じ

定理4

同じ時刻の出来事は、どちらを先に処理しても同じ

定理8

居場所の区間は重ならず、「その時刻の居場所」と一致する

定理5

知識は減らない

一度知ったことを、時間が進んで忘れることはない。

定理6

仕様は矛盾していない

「正しい」と判定されるシナリオが少なくとも1つ存在する。条件が厳しすぎて全部エラーになる、ということはない。

定理7

同じ物を2人は持てない

「A も B も指輪を持つ」ゴールは同時に達成できない。判定器はこの組を正しく割り出す。

定理9

移動時間は1つに決まる

表に重複(R005)がなければ、「書斎→台所は何分か」の答えは1つで、表の書き順によらない。

定理10

投票は「単独最多」か「同数」か

票があれば、どの選択肢でも、単独最多か同数のどちらか一方だけが成り立つ。

定理11

死亡は取り消されない

一度死亡したキャラクターは生き返らず、死亡時刻もぶれない。

第2部

見つかった5つの反例

どれも「同じ内容なのに、書き方(順番・名前)で結果が変わる」か「定理の言い方が少し違っていた」ものです。すべて仕様か定理を直して解消しました。

反例1

出力の並び順が、完全には決まっていなかった

出力は「コード → イベント → 内容 → witness の位置」の順に並べていました。ここまで同じで、重大度など他の部分だけが違う2件があると、どちらを先に出すかが決まっていませんでした。

コードイベント内容witness の位置その他
Xe1[a][0, 1]重大度 error
Xe1[a][0, 1]重大度 warning

このとき、入力の書き順が出力の順に残る可能性がありました(定理3が成り立たない)。

直し方: 比べる項目に「重大度」と「witness の値」を足し、どの2件も必ず順番が決まるようにしました。通常の出力は変わりません。

反例2

イベント ID が重複すると、並べ替えで R011 が変わる

直し方: 同じ ID のイベントのどれか1つでも移動でなければ R011 を出すようにしました。その後、反例5の修正で「ID の重複があれば R001 だけを出す」にもなっています。

反例3

観察される人が、同じ時刻に立ち去る(T012 を新設)

同じ時刻のイベントは、ID の辞書順(a → z)に処理する決まりです。ID は作者が自由に付けるラベルなのに、ここで結果が変わりました。

直し方: この状況を警告 T012 として知らせるようにしました。観察か出発を1分ずらせば解消します。「T012 が出ない ⇔ 定理4の条件が成り立つ」も証明しました。

実例: 「荒木コノミの真相」で1件見つかりました。コノミの転落(18:00)とツムギの遺体発見(18:00)が同時刻です。たまたま ID の順で転落が先だったので、問題が表に出ていませんでした。

反例4

「その時刻の居場所」の意味が2通りあった(定理8の言い直し)

直し方: 「時刻 t までの出来事をすべて処理した後の居場所と一致する」と言い直して証明しました。判定器の動きは変えていません。

反例5

ID が重複すると、並べ替えで R009・R010 が変わる

直し方: ID の重複(R001)があるときは、R001 だけを出すようにしました(仕様 0.5.0)。ID が重複していると「どれのことか」が決まらないので、他の検査には意味がないためです。

補足

反例が見つかった経緯

Lean が「証明できません」とエラーを出したのではありません。証明を組み立てる段階で、必要な条件を漏れなく洗い出した結果「ここで詰まる」と分かり、そこから反例を作りました。

なぜ反例3は普通のテストでは気づきにくいか

方法見つけられたか理由
普通のテスト(入力 → 期待する出力)見つけにくいどちらの ID の付け方でも、出力は単体ではもっともらしい。問題は「名前しか違わない 2 件で結果が違う」という 2 件の関係にある
差分テスト(Lean と試作判定器の比較)見つからなかった両方が同じ仕様を実装しているので、同じ答えを返す。仕様そのものの問題は拾えない(1,000 件以上回していた)
性質を書くテスト(ID を付け替えても結果は同じ)見つけられた可能性はあるその性質を思いつく必要がある。さらに「観察・その対象者の移動・同じ分」がそろう入力はまれで、狙った変異を足すまでほとんど作られていなかった
証明見つかった定理4を証明すると決めたので問いが立ち、読む情報を漏れなく挙げる必要があった。直した後は「これ以外に順序で結果が変わるケースはない」と言える

実際の影響: 「荒木コノミの真相」は、転落と遺体発見がどちらも 18:00 なのに、ID の順(konomi_05 < tsumugi_05)がたまたまよかったので合格していました。テストを書いていても、この「合格」を正解として固定していたはずです。

他の反例も同じ流れで見つかった

反例証明で必要だったことそこで気づいたこと
1 出力の順序「重複がない」を示すには、どの 2 件も必ず前後が決まる必要があるキーが同じで中身が違う 2 件の順序が決まらない
2・5 ID の重複「並べ替えても同じ」を示すには、ID による検索の結果が 1 つに決まる必要があるID が重複すると「最初に見つかったもの」が並び順で変わる
3 観察と同時の出発各検査が読む情報をすべて挙げる必要がある観察の対象者が守られていない
4 居場所の定義定理8の主張を式で書く必要がある同じ時刻の扱いが 2 通りある

5 件とも、見つけた後はオラクル(Lean の判定器)で具体例を作り、本当に起きることを確かめてから直しています。今後はこれらの具体例を回帰テストとして固定し、テストでも守ります。

まとめ: Lean で証明しようとした結果、証明に必要な条件を全部洗い出すことになり、そこで抜けが見つかりました。

第3部

まだ保証していないこと

  • warning(記載漏れ、遭遇の認知など)が、出るべきときに必ず出ること。
  • R 群(構造の検査)の条件を、判定器とは別の命題として書くこと。
  • 検出結果に添える情報(どのキャラクター、どの時刻か)が正しいこと。
  • 配列の要素の中の配列(場面の参加者、選択肢の値など)の並べ替え。
  • 仕様書の日本語の説明と Lean の定義が同じ意味であること。これは証明では確かめられないので、レビューと差分テスト(Lean と Go の出力の比較)で確かめます。
